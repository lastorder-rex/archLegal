# 양성화 프로젝트 · 토스 결제위젯(V2) 연동 개발 스펙

## 1. 문서 개요
- **대상 서비스**: 양성화 프로젝트 웹(Next.js 13 App Router)
- **작성 목적**: 토스 결제위젯(V2 SDK)을 주문서/결제 페이지에 연동하기 위한 기능, 데이터 모델, API, 테스트 요구사항 정의
- **참고 문서**: `docs/project_spec.md`, `docs/모듈별 상세 개발정의서.md`, [Toss Payments 결제위젯 V2 문서](https://docs.tosspayments.com/guides/payment-widget-v2/overview), [llms.txt](https://docs.tosspayments.com/llms.txt)

## 2. 배경 및 목표
- 사용자가 상담 요청 글을 등록한 뒤, 관리자가 전화 등으로 상담을 진행하고 현장 답사를 확정하는 시점에서 결제를 요청하는 흐름을 구축한다.
- 결제 요청은 관리자가 상담글 하단의 `결제요청` 버튼을 통해 발생하며, 사용자는 해당 요청을 기반으로 결제 페이지로 진입한다.
- 결제 수단은 토스 결제위젯 V2 SDK를 활용해 신용/체크카드, 계좌이체 등 위젯 기본 제공 수단으로 시작한다.
- 결제 진행 중 상태 추적, 실패/취소 처리, 관리자용 결제 내역 조회를 지원하기 위한 백오피스 데이터를 마련한다.

## 3. 범위
- **포함**
  - 상담글 상세 화면(관리자/운영자용)에서 결제 요청 발행 기능 (`결제요청` 버튼)
  - 결제 주문 생성 및 토스 결제위젯 연동
  - 결제 승인/실패/취소 시 상태 업데이트 및 영수증 데이터 저장
  - 사용자 결제 페이지 및 성공/실패 후속 페이지 구현
  - 관리자 콘솔(예: `/supercore`)에서의 결제 상태 노출을 위한 API/DB 설계
  - 기본 테스트(단위/통합) 및 시나리오 정의
- **제외**
  - PG 정산/회계 시스템 연동
  - 부가세 계산/전자세금계산서 발행
  - 복수 상품/장바구니 및 정기결제 기능

## 4. 용어 정의
- **주문(Order)**: 결제 대상이 되는 상담/서비스에 대한 결제 요청 단위. DB `orders` 테이블에서 관리.
- **결제(Payment)**: Toss 위젯으로 실제 결제가 승인된 이력. DB `payments` 테이블에서 관리.
- **customerKey**: Toss 위젯용 사용자 식별자. Supabase `users.auth_id` 값 사용.
- **orderId**: Toss 위젯용 주문 식별자. 내부 `orders.id` 기반의 고유 문자열(`ORD-YYYYMMDD-xxxxx`).
- **paymentKey**: Toss에서 결제 승인 후 반환하는 고유 키.

## 5. 시스템 구성 개요
- **프론트엔드**
  - Next.js 13(App Router) + TypeScript
  - 신규 경로
    - 사용자 결제: `app/request/payment/page.tsx`, `app/request/payment/success/page.tsx`, `app/request/payment/fail/page.tsx`
    - 관리자 결제요청 트리거: `app/supercore/consultations/[consultationId]/page.tsx` (기존 페이지에 버튼 추가 가정)
  - 결제 위젯 초기화 컴포넌트: `components/payment/PaymentWidget.tsx` (신규)
  - 결제요청 버튼 컴포넌트: `components/payment/RequestPaymentButton.tsx` (신규, 관리자 전용)
- **백엔드(API Route)**
  - 결제요청 생성: `app/api/admin/consultations/[consultationId]/payment-request/route.ts`
  - 주문 생성: `app/api/payments/order/route.ts`
  - 결제 승인 확정: `app/api/payments/confirm/route.ts`
  - Toss Webhook 수신: `app/api/payments/webhook/route.ts`
  - 관리자 조회: `app/api/admin/payments...[예정]`
- **데이터 저장소**
  - Supabase(PostgreSQL) `orders`, `payments`, `payment_receipts` 테이블 추가
  - `consultations` 테이블과의 연계 필드(`consultations.payment_requested_at`, `consultations.payment_status`) 확장
  - RLS 정책: 사용자별 읽기 제한, 관리자 역할별 전체 접근

## 6. 주요 연동 흐름

### 6.1 상담 → 결제요청 단계
1. 사용자가 상담 요청 글을 `app/request/page.tsx`를 통해 작성하고 제출한다.
2. 관리자는 `/supercore/consultations/[consultationId]` 등 내부 관리 화면에서 상담 글을 확인하고 전화 등으로 상담을 진행한다.
3. 현장 답사를 진행하기로 결정되면 관리자가 상담글 하단의 `결제요청` 버튼을 클릭한다.
4. `POST /api/admin/consultations/[consultationId]/payment-request` 호출:
   - 신규 주문 레코드(`orders`) 생성 및 `consultations.payment_requested_at` 업데이트
   - 사용자에게 결제 안내(알림톡/이메일 등은 후속 과제) 및 결제 페이지 링크 정보 반환
5. 사용자는 마이페이지 상담글 상세 또는 안내받은 링크에서 `결제하기` 버튼을 통해 `/request/payment?orderCode=...`로 이동한다.

### 6.2 결제 진행 단계
1. 결제 페이지 진입 시 `POST /api/payments/order` 호출(`orderCode` 포함) → 해당 주문의 유효성 확인 및 재발급(필요 시).
2. 응답(`orderId`, `amount`, `customerKey`, `widgetsOptions`)을 기반으로 V2 위젯 초기화.
3. 사용자가 결제 수단 선택 및 약관 동의 후 결제 요청 → Toss 위젯이 `/request/payment/success`, `/request/payment/fail`로 리디렉션.
4. 성공 페이지에서 `paymentKey`, `orderId`, `amount` 쿼리 파라미터 확보 후 `POST /api/payments/confirm` 호출.
5. 백엔드에서 Toss Secret Key로 결제 승인 API 호출 → 성공 시 `payments` 테이블 상태 업데이트, 영수증 정보 저장.
6. Webhook(`/api/payments/webhook`)으로 추가 상태 변경(예: 취소, 부분환불) 수신 → DB 업데이트 및 알림 처리.

## 7. 데이터 모델 설계

### 7.1 orders
```sql
create table public.orders (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users,
  consultation_id uuid references public.consultations,
  order_code text not null unique, -- 예: ORD-20240214-00001
  order_name text not null,
  amount integer not null, -- KRW (단위: 원)
  currency text not null default 'KRW',
  status text not null default 'pending', -- pending | paid | failed | canceled
  expires_at timestamptz not null,
  metadata jsonb default '{}'::jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```
- `user_id`: Supabase auth user 식별자
- `consultation_id`: 기존 상담 신청 레코드 연결(옵션)
- `status`: 결제 승인 시 `paid`, 실패 시 `failed`, 사용자가 취소하면 `canceled`
- `expires_at`: 결제 대기 만료시간(예: 주문 생성 후 30분)

### 7.2 payments
```sql
create table public.payments (
  id uuid primary key default gen_random_uuid(),
  order_id uuid not null references public.orders on delete cascade,
  payment_key text not null unique,
  method text, -- 카드, 계좌이체 등
  approved_at timestamptz,
  canceled_at timestamptz,
  status text not null default 'pending', -- pending | approved | canceled | failed
  failure_code text,
  failure_message text,
  receipt_url text,
  raw_response jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```
- 주문과 1:1을 기본으로 가정(부분 결제/재시도는 차후 확장 시 `sequence` 컬럼 추가 고려).

### 7.3 payment_receipts (옵션)
```sql
create table public.payment_receipts (
  id uuid primary key default gen_random_uuid(),
  payment_id uuid not null references public.payments on delete cascade,
  type text not null, -- approval | cancel | partial_cancel 등
  payload jsonb not null,
  created_at timestamptz not null default now()
);
```
- Toss Webhook 또는 승인/취소 API 응답 전문 보관용.

### 7.4 consultations 확장
```sql
alter table public.consultations
  add column payment_status text default 'pending', -- pending | requested | paid | canceled | failed
  add column payment_requested_at timestamptz,
  add column payment_completed_at timestamptz;
```
- 결제요청 버튼 클릭 시 `payment_status`를 `requested`로, 완료 시 `paid`로 업데이트
- 필요 시 결제 실패/취소 사유를 위한 `payment_notes`(text) 추가 검토

### 7.5 RLS 정책 개요
- 기본: `user_id = auth.uid()` 일치 시 본인 주문/결제 조회 허용.
- 관리자 역할(`admin_users` 테이블 기반)에게는 전체 읽기/수정 허용.
- Webhook/서버 라우트는 `service_role` 키를 사용하므로 RLS 예외 처리 필요.

## 8. 환경 변수 & 설정

- `components/payment/PaymentWidget.tsx`
  - 클라이언트 컴포넌트, Suspense/Loading 처리
  - 예시 코드:
    ```tsx
    import { loadPaymentWidget } from '@tosspayments/payment-widget-sdk';
    import { useEffect, useState } from 'react';

    export function PaymentWidget({ clientKey, customerKey, order }) {
      const [widget, setWidget] = useState(null);

      useEffect(() => {
        let mounted = true;

        async function init() {
          const paymentWidget = await loadPaymentWidget(clientKey, customerKey);
          if (!mounted) return;

          await paymentWidget.renderPaymentMethods('#payment-method', order.amount, {
            variantKey: 'DEFAULT'
          });
          await paymentWidget.renderAgreement('#agreement', { variantKey: 'DEFAULT' });
          setWidget(paymentWidget);
        }

        init();
        return () => { mounted = false; };
      }, [clientKey, customerKey, order.amount]);

      const handleRequestPayment = async () => {
        if (!widget) return;
        await widget.requestPayment({
          orderId: order.orderCode,
          orderName: order.orderName,
          successUrl: `${window.location.origin}/request/payment/success`,
          failUrl: `${window.location.origin}/request/payment/fail`
        });
      };

      return (
        <>
          <div id="payment-method" />
          <div id="agreement" className="mt-4" />
          <button onClick={handleRequestPayment}>결제하기</button>
        </>
      );
    }
    ```
- 성공/실패 페이지(`success`, `fail`)는 CSR 컴포넌트로 QueryString(`orderId`, `paymentKey`, `amount`, `code`, `message`) 읽어 처리.

### 9.3 상태 관리 & 검증
- 관리자 버튼: 이미 `requested` 이상 상태일 경우 비활성화, 실패 시 오류 토스트 표시.
- 주문 생성 실패 시 사용자에게 재시도 버튼 제공.
- `amount`는 서버에서 내려준 값을 UI에 그대로 표시(클라이언트 수정 차단).
- 결제 요청 전 이용 동의 체크 완료 여부를 프론트에서 확인.

## 10. 백엔드(API) 상세

### 10.1 결제요청 생성 `POST /api/admin/consultations/[consultationId]/payment-request`
- **Auth**: 관리자 전용(`admin_users` 역할 검사)
- **Request Body**
  ```json
  {
    "amount": 88000,
    "orderName": "양성화 프로젝트 현장답사 서비스"
  }
  ```
- **Logic**
  1. 상담글 소유자 조회 및 이미 결제 완료/진행 중인지 확인
  2. 기존 결제 요청이 `requested` 상태이고 주문이 유효하면 재사용, 아니면 신규 주문 생성
  3. `consultations.payment_status` → `requested`, `payment_requested_at = now()`
  4. 생성된 주문 정보 및 결제 링크(`/request/payment?orderCode=...`) 반환
- **Response**
  ```json
  {
    "order": {
      "orderCode": "ORD-20240214-00001",
      "orderName": "양성화 프로젝트 현장답사 서비스",
      "amount": 88000
    },
    "payLink": "https://domain/request/payment?orderCode=ORD-20240214-00001"
  }
  ```

### 10.2 주문 생성 `POST /api/payments/order`
- **Request Body**
  ```json
  {
    "orderCode": "ORD-20240214-00001",
    "consultationId": "OPTIONAL_UUID"
  }
  ```
- **Auth**: 로그인 쿠키 기반 `createRouteHandlerClient`
- **Logic**
  1. 사용자 세션 확인 → 미로그인 시 401 반환
  2. `orderCode`로 주문 조회, 세션 사용자와 매칭, 상태가 `pending` 또는 `requested`인지 확인
  3. 주문이 만료되었으면 새 주문을 생성하고 기존 주문은 `canceled` 처리
  4. 응답으로 최신 `order`, `customerKey`, `clientKey`, `amount` 반환
- **Response**
  ```json
  {
    "order": {
      "orderCode": "ORD-20240214-00001",
      "orderName": "양성화 프로젝트 상담 수수료",
      "amount": 88000
    },
    "customerKey": "auth-user-uuid",
    "clientKey": "NEXT_PUBLIC_TOSS_CLIENT_KEY"
  }
  ```

### 10.3 결제 승인 `POST /api/payments/confirm`
- **Request Body**
  ```json
  {
    "orderId": "ORD-20240214-00001",
    "paymentKey": "string",
    "amount": 88000
  }
  ```
- **Auth**: 로그인 쿠키 + 주문 소유자 검증
- **Logic**
  1. 주문/amount 일치 여부 검증 → mismatch 시 400
  2. Toss Confirm API 호출
     ```http
     POST https://api.tosspayments.com/v2/payments/confirm
     Authorization: Basic base64(TOSS_SECRET_KEY:)
     Content-Type: application/json
     Body: { "paymentKey", "orderId", "amount" }
     ```
  3. 성공 시:
     - `orders.status` → `paid`, `payments.status` → `approved`
     - 결제 메서드, 승인 일시, 영수증 URL 저장
     - 상담 진행 상태 업데이트(예: `consultations.payment_status = 'paid'`, `payment_completed_at = now()`)
  4. 실패 시:
     - 실패 사유 저장 후 400/500 응답
     - 필요 시 `consultations.payment_status = 'failed'`, `payment_notes` 업데이트

### 10.4 Webhook `POST /api/payments/webhook`
- **Security**: Toss가 제공하는 `SecretKey` 기반 시그니처 검증 헤더(`Toss-Signature`) 확인
- **지원 이벤트**
  - `PAYMENT_STATUS_CHANGED` (취소/부분취소 포함)
- **처리**
  - `paymentKey`로 `payments` 조회 → 상태 업데이트
  - 취소 금액이 주문 총액과 동일하면 `orders.status`도 `canceled`
  - 이벤트 payload를 `payment_receipts`에 저장
  - 관리자 알림(슬랙 등)은 후속 과제로 분리

### 10.5 관리자 조회 API (로드맵)
- `GET /api/admin/payments` : 필터(사용자, 상태, 기간) 제공
- Supabase service role 또는 RLS bypass

## 11. 예외/실패 시나리오
- 주문 만료(`expires_at < now`) → 프론트에서 알림 후 새 주문 생성 요청
- 결제 실패 (`failUrl`): Toss가 전달하는 `code`, `message`를 사용자에게 노출하고, 주문 상태 `failed`로 업데이트
- 결제 중 복수 탭에서 동시도전 → 첫 승인만 성공, 나머지 요청은 Toss `ALREADY_PROCESSED` 오류 → 프론트에서 처리
- Webhook 지연 시: 성공 페이지 확인과 상태 불일치 가능 → `confirm` API 완료 시 바로 `approved` 처리 후 Webhook은 이벤트만 기록

## 12. 보안 및 준수 사항
- Secret Key는 서버 전용, 절대 클라이언트에 노출하지 않는다.
- API 라우트는 CSRF 방어를 위해 POST 전송 시 `SameSite=Lax` 쿠키 정책 유지.
- 주문 금액은 클라이언트 입력이 아닌 서버 계산을 사용.
- Toss Webhook URL은 HTTPS(프로덕션) 필수, 로컬 테스트 시 `ngrok` 등 터널링 도구 사용.

## 13. 로컬/스테이징 테스트 플로우
- Toss에서 발급받은 테스트 키 사용
- 성공 케이스
  1. 주문 생성 → 위젯 호출 → 테스트 카드(1234-1234-1234-1234 등)로 결제 → 성공 페이지 `결제 완료` 확인
  2. Supabase `orders`, `payments` 상태 확인
- 실패 케이스
  - 결제 취소 카드 사용, 금액 불일치 시도(`amount` 조작) → 서버에서 400 반환 확인
- Webhook
  - Toss 테스트 대시보드에서 취소 이벤트 전송 → `payments.status`가 `canceled`로 업데이트되는지 확인
