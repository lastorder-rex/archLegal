# 양성화 프로젝트 · 토스 결제위젯(V2) 연동 개발 스펙

## 1. 문서 개요
- **대상 서비스**: 양성화 프로젝트 웹(Next.js 14 App Router)
- **작성 목적**: 토스페이먼츠 Web SDK(v2, widgets)를 마이페이지 결제 단계(Stage) UI에 연동하기 위한 기능, 데이터 모델, API, 테스트 요구사항 정의
- **참고 문서**: `docs/모듈별 상세 개발정의서.md`,
  - 결제 위젯 v2 가이드: https://docs.tosspayments.com/guides/payment-widget/integration
  - 시작하기(v2): https://docs.tosspayments.com/guides/v2/get-started

## 2. 배경 및 목표
- 사용자가 상담 글을 등록하면, 관리자가 단계별로 결제 요청(예: 1단계 현장답사, 2단계 양성화 대행)을 발행한다.
- 사용자는 마이페이지 > 결제 탭에서 활성화된 결제 단계를 확인하고, 해당 카드에서 직접 결제를 진행한다.
- 결제는 토스페이먼츠 Web SDK(v2)의 위젯을 사용하며, 결제 성공 시 성공 페이지에서 서버 `confirm` API로 승인 확정을 수행한다.
- 관리자와 사용자가 각각 결제 상태(요청됨/대기/완료)를 추적할 수 있는 데이터 모델과 API를 제공한다.

## 3. 범위
- 포함
  - 관리자 페이지에서 결제 단계(Stage) 요청 발행/취소(예: 1단계 현장답사 비용)
  - 마이페이지 > 결제 탭에서 결제 위젯 초기화 및 결제 진행(UI/UX)
  - 결제 성공/실패 페이지 처리 및 서버 `confirm` 승인 확정 API 연동
  - 사용자별 단계 상태 조회 API(`/api/payments/stages`)
  - 기본 테스트(단위/통합) 및 시나리오 정의
- 제외(현 시점)
  - PG 정산/회계 시스템 연동
  - 전자세금계산서/영수증 발행 저장소(Webhook 포함) — 후속 과제로 분리
  - 복수 상품/장바구니 및 정기결제 기능

## 4. 용어 정의
- 결제 단계(Stage): 결제해야 하는 업무 단계(예: `site_survey`, `legalization`). 템플릿과 사용자별 진행 상태로 관리.
- 사용자 결제 단계(User Stage): 특정 사용자의 특정 단계 진행 상태. `locked | requested | awaiting | paid` 중 하나.
- customerKey: Toss 위젯용 사용자 식별자. Supabase `users.auth_id` 또는 식별 가능한 대체 키.
- orderId: Toss 위젯 결제 식별자. 현재는 프론트에서 단계ID 기반 임시 생성(`ORD-...`) 후 성공 페이지에서 서버 승인(confirm) 시 사용.
- paymentKey: Toss가 결제 성공 시 반환하는 고유 키. 서버 confirm 호출에 필요.

## 5. 시스템 구성 개요
- 프론트엔드
  - Next.js 14(App Router) + TypeScript
  - 사용자 경로: `app/mypage/payments/success/page.tsx`, `app/mypage/payments/fail/page.tsx`
  - 마이페이지 결제 섹션: `components/mypage/MyPagePaymentsSection.tsx` (위젯 로드/결제 요청)
  - 관리자 화면: `app/supercore/consultations/[consultationId]/page.tsx` 내 결제요청 트리거
- 백엔드(API Route)
  - 결제 단계 요청/취소: `app/api/admin/consultations/[id]/payment-request/route.ts` (POST/DELETE)
  - 사용자 단계 조회: `app/api/payments/stages/route.ts` (GET)
  - 결제 승인 확정: `app/api/payments/confirm/route.ts` (POST)
- 데이터 저장소
  - Supabase(PostgreSQL): `payment_stage_templates`, `user_payment_stages`, `payment_notifications`
  - RLS 정책: 사용자별 읽기 제한, 관리자 역할 전체 접근(서버 키)

### 5.1 개발 환경 준비
- SDK 설치: `npm install @tosspayments/tosspayments-sdk`
- **환경 변수 설정** (`.env.local` 등)
  ```bash
  NEXT_PUBLIC_TOSS_CLIENT_KEY=테스트/운영 client key
  TOSS_SECRET_KEY=테스트/운영 secret key
  ```
- 환경 변수를 추가한 뒤 개발 서버를 재시작(`npm run dev`)해 위젯 초기화 코드가 최신 값을 참조하도록 한다.

## 6. 주요 연동 흐름

### 6.1 상담 → 결제요청 단계(스테이지 기반)
1. 사용자가 상담을 등록한다.
2. 관리자는 `/supercore/consultations/[id]`에서 상담을 검토하고, 결제가 필요한 단계(예: 1단계 현장답사)를 선택해 금액과 함께 결제 요청을 발행한다.
3. 서버는 `user_payment_stages`에 해당 단계 레코드를 `awaiting` 상태로 생성/업데이트하고, 알림 큐(`payment_notifications`)에 기록한다.
4. 사용자는 마이페이지 > 결제 탭에서 활성화된 단계 카드와 금액을 확인한다.

### 6.2 결제 진행 단계(마이페이지)
1. 마이페이지 결제 탭에서 단계 카드의 ‘결제 진행’ 버튼을 누르면 위젯이 로드된다.
2. SDK는 `@tosspayments/tosspayments-sdk`의 `widgets()`를 사용하며, `setAmount`로 서버가 지정한 금액을 설정한 뒤 수단/약관을 렌더링한다.
3. 사용자가 결제를 요청하면 Toss 위젯이 `/mypage/payments/success` 또는 `/mypage/payments/fail`로 리디렉션한다.
4. 성공 페이지는 QueryString(`orderId`, `paymentKey`, `amount`)을 서버 `POST /api/payments/confirm`에 전달하여 승인 확정을 수행한다.
5. 승인 성공 시 `user_payment_stages`의 상태를 `paid`로 업데이트하고 `paid_at`, `paid_amount`, `payment_key`를 저장한다. (현재 코드: 승인 API 스켈레톤 존재, DB 반영 로직은 추가 예정)

## 7. 데이터 모델 설계(현행)

### 7.1 payment_stage_templates
반복 사용 가능한 결제 단계 템플릿. `supabase/migrations/016_add_payment_stage_tables.sql` 참조.
```sql
create table public.payment_stage_templates (
  id uuid primary key default gen_random_uuid(),
  stage_order integer not null,
  code text unique not null,
  title text not null,
  description text,
  default_amount numeric(12,2),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

### 7.2 user_payment_stages
사용자별 단계 진행 상태 및 금액/키를 저장. 상태: `locked | requested | awaiting | paid`.
```sql
create table public.user_payment_stages (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.users (auth_id) on delete cascade,
  consultation_id uuid references public.consultations (id) on delete set null,
  stage_template_id uuid not null references public.payment_stage_templates (id) on delete restrict,
  status text not null default 'locked',
  request_amount numeric(12,2),
  requested_at timestamptz,
  requested_by uuid references public.admin_users (id) on delete set null,
  paid_at timestamptz,
  paid_amount numeric(12,2),
  payment_key text,
  last_notified_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create unique index user_payment_stage_unique_idx on public.user_payment_stages (user_id, stage_template_id);
```

### 7.3 payment_notifications
결제 요청/취소 등 알림 큐/로그. (카카오 알림톡 등 후속 연동용)
```sql
create table public.payment_notifications (
  id uuid primary key default gen_random_uuid(),
  user_payment_stage_id uuid not null references public.user_payment_stages (id) on delete cascade,
  notification_type text not null,
  payload jsonb,
  sent_at timestamptz,
  created_at timestamptz not null default now()
);
```

### 7.4 RLS 정책 개요
- 기본: `user_id = auth.uid()` 일치 시 본인 단계만 조회 가능
- 관리자(`admin_users`)는 서버 키로 전체 접근

## 8. 환경 변수 & 설정
- `NEXT_PUBLIC_TOSS_CLIENT_KEY`: 위젯 초기화용 퍼블릭 키 (브라우저 공개 가능)
- `TOSS_SECRET_KEY`: 서버에서 Toss REST API 호출 시 Basic Auth로 사용(confirm)
- 성공/실패 URL은 코드에서 `window.location.origin` 기반으로 계산(별도 env 불필요)

## 9. 프론트엔드 개발 상세

### 9.1 의존성
```bash
npm install @tosspayments/tosspayments-sdk
```

### 9.2 페이지/컴포넌트 구조(현행)
- 관리자 결제요청: `app/supercore/consultations/[id]/page.tsx`에서 호출하는 API — `POST /api/admin/consultations/[id]/payment-request`
- 사용자 결제: `components/mypage/MyPagePaymentsSection.tsx`에서 위젯 로드 및 결제 요청
- 성공/실패 페이지: `app/mypage/payments/success/page.tsx`, `app/mypage/payments/fail/page.tsx`

위젯 로드/요청 예시(요약):
```tsx
import { loadTossPayments } from '@tosspayments/tosspayments-sdk';

const toss = await loadTossPayments(process.env.NEXT_PUBLIC_TOSS_CLIENT_KEY!);
const widget = await toss.widgets({ customerKey });
await widget.setAmount({ value: amount, currency: 'KRW' });
await widget.renderPaymentMethods({ selector: '#payment-widget', variantKey: 'DEFAULT' });
await widget.renderAgreement({ selector: '#payment-agreement', variantKey: 'AGREEMENT' });

await widget.requestPayment({
  orderId,
  orderName,
  successUrl: `${origin}/mypage/payments/success`,
  failUrl: `${origin}/mypage/payments/fail`,
  metadata: { amount }
});
```

### 9.3 상태 관리 & 검증
- 관리자 버튼: 이미 `requested` 이상 상태일 경우 비활성화, 실패 시 오류 토스트 표시.
- 주문 생성 실패 시 사용자에게 재시도 버튼 제공.
- `amount`는 서버에서 내려준 값을 UI에 그대로 표시(클라이언트 수정 차단).
- 결제 요청 전 이용 동의 체크 완료 여부를 프론트에서 확인.

## 10. 백엔드(API) 상세

### 10.1 결제요청 생성/취소
`POST /api/admin/consultations/[id]/payment-request` (생성), `DELETE /api/admin/consultations/[id]/payment-request` (취소)
- **Auth**: 관리자 전용(`admin_users` 역할 검사)
- **Request Body**
  ```json
  {
    "stageTemplateId": "uuid",
    "amount": 88000
  }
  ```
- **Logic**
  1. 상담글/사용자 확인 및 단계 선행 조건 충족 검증
  2. `user_payment_stages` upsert: `locked` → `awaiting`로 전환, 금액/요청자/요청시각 기록
  3. `payment_notifications`에 `payment_request_created` 기록(실패 시 롤백)
  4. 최종 사용자 단계 상태 반환

### 10.2 사용자 단계 조회 `GET /api/payments/stages`
- **Auth**: 로그인 세션 필수
- **Response**: 사용자별 단계 목록(`id, title, status, requestAmount, requestedAt, paidAt, paidAmount, paymentKey, nextActionLabel, disabled`)

### 10.3 결제 승인 `POST /api/payments/confirm`
- **Request Body**
  ```json
  {
    "orderId": "ORD-20240214-00001",
    "paymentKey": "string",
    "amount": 88000
  }
  ```
- **Auth**: 로그인 쿠키 + 주문 소유자 검증
- **Logic**
  1. 금액/식별자 유효성 검증 → mismatch 시 400
  2. Toss Confirm API 호출
     ```http
     POST https://api.tosspayments.com/v2/payments/confirm
     Authorization: Basic base64(TOSS_SECRET_KEY:)
     Content-Type: application/json
     Body: { "paymentKey", "orderId", "amount" }
     ```
  3. 성공 시:
     - `user_payment_stages.status` → `paid`
     - `paid_at`, `paid_amount`, `payment_key` 업데이트
  4. 실패 시:
     - 실패 사유 저장 후 400/500 응답
     - 필요 시 에러 로깅/알림 처리

### 10.4 Webhook (후속 과제)
- 향후 취소/부분취소 등 상태 변경을 위한 Webhook 엔드포인트 추가 예정

### 10.5 관리자 조회 API (로드맵)
- `GET /api/admin/payments` : 필터(사용자, 상태, 기간) 제공
- Supabase service role 또는 RLS bypass

## 11. 예외/실패 시나리오
- 결제 실패(`failUrl`): Toss가 전달하는 `code`, `message`를 사용자에게 노출
- 동시 결제 시도: 첫 승인만 성공, 나머지는 Toss `ALREADY_PROCESSED` 오류 → 프론트에서 안내
- 승인 지연: 성공 페이지에서 `confirm` API를 우선하여 사용자 단계 상태를 `paid`로 반영, Webhook은 추후 이벤트 기록용으로 사용 예정

## 12. 보안 및 준수 사항
- Secret Key는 서버 전용, 절대 클라이언트에 노출하지 않는다.
- API 라우트는 CSRF 방어를 위해 POST 전송 시 `SameSite=Lax` 쿠키 정책 유지.
- 주문 금액은 클라이언트 입력이 아닌 서버 계산을 사용.
- Toss Webhook URL은 HTTPS(프로덕션) 필수, 로컬 테스트 시 `ngrok` 등 터널링 도구 사용.

## 13. 로컬/스테이징 테스트 플로우
- 테스트 키 사용(클라이언트/시크릿)
- 성공 케이스
  1. 관리자 화면에서 단계 요청 생성(금액 지정)
  2. 마이페이지 결제 탭에서 단계 카드 ‘결제 진행’ → 테스트 카드로 결제 → 성공 페이지 도달
  3. 성공 페이지에서 `POST /api/payments/confirm` 호출 정상 응답 확인 → 사용자 단계가 `paid`로 반영되는지 확인(DB 로직 추가 후)
- 실패 케이스
  - 결제 취소 카드 사용, 금액 불일치 시도 → 오류 메시지/코드 확인
- Webhook
  - 후속 과제. 현재는 confirm 기반으로 상태 반영

## 14. 구현 일정 제안(현행 흐름 기준)
1. 사전 준비 (0.5d): 테스트 키 발급, env 설정, SDK 설치
2. DB 마이그레이션 (0.5d): `payment_stage_templates`, `user_payment_stages`, RLS 작성
3. API 개발 (1.0d): 결제요청(POST/DELETE), 사용자 단계 조회(GET), confirm(POST)
4. 프론트 UI (1.0d): 마이페이지 결제 탭 위젯 로드/요청, 성공/실패 페이지
5. 통합 테스트 (1d): 시나리오별 테스트, 관리자 뷰 연동
6. QA & 문서화 (0.5d): 테스트 케이스 기록, 운영 매뉴얼 업데이트
