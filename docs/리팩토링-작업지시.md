# 리팩토링 작업 지시

$ARGUMENTS 에 지정된 범위(없으면 사용자에게 범위 확인)를 아래 원칙으로 리팩토링한다.

## 제1원칙 (최우선, 위반 불가)
**기존 동작과 UI 디자인의 완전한 보존.**
- 모든 변경은 외부에서 관찰 가능한 동작·렌더링 결과(DOM 구조·className·텍스트·네트워크 요청 시점/횟수·응답 바디)가 리팩토링 전과 동일해야 함
- 동작 변경이 불가피하다고 판단되는 지점은 수정하지 말고 보고서에 기록만 할 것
- 확신이 없는 변경은 수행하지 않음 (보수적 접근)

## 목표
코드베이스를 "더 직관적으로 찾고, 더 빠르게 수정할 수 있는" 구조로 개선한다.

## 작업 범위
1. **구조 체계 고도화** — 디렉토리 구조, 파일 분류, 라우트/API 네이밍을 일관 규칙으로 재정비 (규칙을 먼저 정의하고 일관 적용)
2. **중복 제거 및 통합** — 중복 컴포넌트·훅·유틸·타입·로직을 단일 소스로 통합. 사용처 전부 추적해 누락 없이 교체
3. **UI 코드 가시성** (선택) — 자주 수정되는 가변 UI와 고정 셸을 구분 배치

## 진행 절차 (필수 순서)
1. **읽기 전용 분석 먼저** — 병렬 서브에이전트로 범위를 나눠(페이지/API/횡단) 수정 후보 목록 작성. 각 항목에 근거(파일:줄)·제안·위험도(하/중/상)·규모 표기
2. **분석 결과를 사용자에게 표로 보고**하고 실행 범위 승인받기 (위험도 상 항목은 보류 권고로)
3. **tsc 기준선 측정** 후 시작 (기준 = 기준선 유지)
4. 승인된 항목을 **위험도 낮은 것부터 단계별 실행** — 파일이 겹치지 않으면 병렬, 겹치면 순차
5. **매 단계: tsc 통과 확인 → diff 스팟체크(추출 이외 변화 없는지) → 커밋(체크포인트)** — 되돌리기 쉬운 단위 유지

## 실행 시 주의 (실전 교훈)
- **분석 에이전트의 전제를 실행 전에 직접 재검증**할 것 (예: "외부 임포트 0건" 같은 주장 — grep으로 재확인. 틀린 전제로 이동하면 범위 밖 파일을 건드리게 됨)
- 타입 통합: **필드가 하나라도 다르면 합치지 말 것** (optional로 뭉개기 금지). 동명이형은 별도 이름으로 분리
- 포매터/헬퍼 통합: **변형(가드·로케일·철자 차이)을 통일하지 말고 변형별 함수로 보존**. import 별칭으로 호출부 무변경
- UI 추출: className 문자 단위 보존. 두 곳이 다르면 prop으로 차이를 보존하거나 공용화 포기
- 훅 추출(인증·로딩 등): useEffect 의존성 연쇄로 생기는 **기존 quirk(재호출 타이밍)까지 재현**해야 동작 보존. 재현 불가하면 그 페이지는 스킵
- Tailwind: 동적 클래스 조합(`bg-${x}`) 금지 — purge에서 깨짐. 완성 리터럴로
- 커밋은 리팩토링 파일만 정확히 스테이징 (작업 중인 다른 미커밋 변경과 섞지 말 것)

## 제약 사항
- **허용**: `tsc --noEmit` 타입체크 (적극 활용)
- **금지**: 빌드 실행, Playwright 등 실행 기반 검증
- **제외**: 성능·최적화 작업 (발견한 권장사항은 메모로만 축적)

## 실행 방식
- 실제 코딩은 서브에이전트(Opus급 모델)에 위임하고, 메인은 분석·지시·검수를 담당
- 서브에이전트 지시에는 제1원칙·대상 파일 경계·검증 방법·"확신 없으면 스킵하고 보고" 조항을 반드시 포함
- 대규모 변경은 단계 분할, 각 단계 tsc 통과 후 진행

## 결과 보고 (작업 완료 시)
1. 변경 요약: 통합·이동·삭제된 항목 목록 (커밋 해시 포함)
2. 구조 Before / After 트리
3. 최적화 권장사항 메모 (미수행 항목)
4. 동작 보존이 불확실하여 보류한 지점과 이유
