# Codex Review 문서 기준

## 1. 목적과 적용 범위
- Codex가 수행하는 코드·문서 리뷰 결과물을 일관되고 재사용 가능한 형식으로 정리하기 위한 기준이다.
- 신규 기능, 버그 수정, 문서 개정 등 변경 사항에 대해 리뷰 피드백을 작성할 때 사용한다.
- 본 기준은 리뷰 산출물 작성자(에이전트)와 검토자(사용자) 모두에게 동일하게 적용된다.

## 2. 리뷰 준비 절차
- 변경 의도, 요구사항, 테스트 범위 등 맥락을 먼저 정리한다.
- 리뷰 대상의 파일 목록을 훑어 의존 관계, 주요 흐름을 파악한다.
- 필요 시 기존 규칙(코딩 컨벤션, 보안 가이드, 성능 목표 등)을 확인한다.
- 산출물 작성 전에 잠정적인 흥미/위험 포인트를 메모해 우선순위를 세운다.

## 3. 리뷰 산출물 구조
1. **Findings**: 심각도가 높은 항목부터 기재한다.
   - 형식: `- (심각도) 파일경로:라인 - 문제 요약`
   - 각 항목에는 영향 범위와 재현 가능성, 제안(해결 방향 또는 확인 요청)을 반드시 포함한다.
2. **Open Questions / Assumptions**: 검토 중 추가 맥락이 필요한 사항이나 가정한 전제를 정리한다.
3. **Additional Notes**: 선택적으로 제공한다. 요약, 테스트 제안, 리팩터링 아이디어 등.

## 4. 심각도 레벨 정의
- **Critical**: 기능 오작동, 보안 취약점, 데이터 손실 등 즉시 수정이 필요한 문제.
- **Major**: 기능 요구사항 미충족, 성능·확장성 저하, 테스트/문서 주요 누락 등 출시 전 해결이 필요한 문제.
- **Minor**: 유지보수성, 가독성, 일관성 등을 개선할 수 있는 항목. 출시 가능하나 추후 정비 권장.
- **Nit**: 스타일·취향 차이 등 영향이 극히 낮은 의견. 명확한 근거가 있을 때만 제안.

## 5. 필수 검토 항목 체크리스트
- **Correctness**: 요구사항과 실제 동작이 일치하는가?
- **Regressions**: 기존 기능에 부작용을 일으키지 않는가?
- **Robustness / Security**: 엣지 케이스, 오류 처리, 보안 위협에 대응하는가?
- **Performance**: 예상되는 데이터·트래픽 규모에서 병목이나 과도한 자원 사용이 없는가?
- **Maintainability**: 코드 구조, 재사용성, 테스트 가능성이 충분한가?
- **Tests & Docs**: 자동화 테스트 및 문서가 충분하고 정확하게 갱신되었는가?

## 6. 작성 스타일 가이드
- 간결하고 정확한 한국어 문장을 사용하되, 코드·경로·명령은 `inline code`로 표기한다.
- 지적보다는 문제 상황과 영향, 해결 방안을 중심으로 협업 친화적으로 설명한다.
- 동일 파일에서 여러 문제가 발견되면 한 항목에 묶지 말고 개별 항목으로 분리한다.
- 사용자 요청이 없는 한 산출물에 실행 로그 전체를 붙이지 않고, 핵심 증거만 요약한다.

## 7. 프로젝트별 준수 규칙
- **기본 코드 스타일**: Prettier 설정, ESLint 규칙, TypeScript 사용 원칙 등 팀 컨벤션을 위반하는 변경은 없는지 확인한다. 관련 규칙은 `package.json` 스크립트와 `.eslintrc` 참고.
- **폴더 구조 규칙**: `docs/folder-structure.md`에서 정의한 `app/`, `core/`, `services/`, `api/` 등 모듈 위치가 지켜졌는지 검토한다.
- **Supabase 보안 규칙**: RLS 정책, 서비스 키 사용 범위 등 `supabase/` 및 관련 문서의 가이드에 맞게 구현됐는지 확인한다.
- **인증/권한 규칙**: `lib/auth/` 유틸과 미들웨어가 올바르게 사용되어 권한 체크가 누락되지 않았는지 검토한다.
- **DB 트랜잭션 규칙**: 다중 업데이트/인서트가 필요한 경우 트랜잭션 처리와 롤백 전략이 적용됐는지 확인한다.
- **파일 업로드 보안 규칙**: 파일 크기/확장자 검증, 임시 URL 만료 등 업로드 정책을 준수했는지 살핀다.
- **Toss 결제 보안 룰**: `docs/양성화프로젝트_토스_결제위젯_연동_개발스팩.md`의 키 관리, 서명 검증, 콜백 검증 규칙을 리뷰한다.
- **로그/모니터링 규칙**: 민감 정보 마스킹, 감사 로그 누락 여부 등 운영 기준을 확인한다.
- **코드 리뷰 체크리스트**: 상기 항목을 토대로 새 이슈나 예외 사항을 추가 목록으로 축적한다.

## 8. 부록: 예시 템플릿
```
Findings
- (Major) app/api/user.ts:57 - 새 비밀번호 검증이 누락되어 빈 문자열이 저장됩니다. 인증 후 `validatePassword`를 호출해 비어 있지 않은지 확인해야 합니다.
- (Minor) components/Card.tsx:12 - `CardHeader`가 optional인데 default props가 없어 런타임 경고가 발생합니다. 기본값을 추가하거나 조건부 렌더링을 적용해주세요.

Open Questions / Assumptions
- 사용자 생성 API에서 비밀번호 정책이 프론트에서만 enforce된다고 이해했는데, 서버에서도 검증해야 하는지 확인이 필요합니다.

Additional Notes
- 변경된 API에 맞춰 e2e 테스트 `tests/auth.spec.ts` 업데이트를 제안드립니다.
```

## 9. 유지 관리
- 기준은 프로젝트 컨벤션, 리뷰 프로세스 변화에 따라 주기적으로 개정한다.
- 변경 시 개정 이력(날짜, 개정자, 주요 변경)을 문서 하단에 추가한다.
